## Cuidados ao trabalhar

- O usuário não entende de Git nem de terminal: execute você mesmo os comandos, explique resultados em linguagem simples e peça só o que depender dele (login no navegador, dados de conta). Antes de qualquer coisa que altere Supabase, Cloudflare ou envios de e-mail, explique e espere aprovação.
- Git: branch `main`, repositório privado `clinicatorricelli-rgb/clinica-torricelli` no GitHub (primeiro commit em 09/11/2026). Não executar limpeza/reset que apague trabalho; `artifacts/` e outros arquivos ignorados existem só no computador do escritório.
- **Publicação automática:** todo push/merge em `main` roda `.github/workflows/publicar-site.yml` (testes locais → build `staging` conectado → `scripts/check-bundle.mjs` → `wrangler pages deploy` no projeto existente `clinica-torriceli-previa`, mesmo endereço). Pull requests só testam e montam, sem publicar. Portanto: trabalhar em branch + PR e só mesclar em `main` o que pode ir ao ar. Voltar versão: painel do Cloudflare Pages → Deployments → Rollback. O fluxo publica apenas o frontend; não altera banco, funções, Auth ou e-mails.
- Sessões na nuvem não têm `artifacts/`, login da CLI Supabase nem do Wrangler. **Desde 13/11 há um token pessoal do Supabase salvo nas configurações da nuvem** (trocado em 21/11 por um token por projeto: o valor em Network secrets precisa começar com `Bearer `; permissões: Project Settings read, Logs read, Database read-write, Auth Config read-write, Edge Functions read-write) (salvo pelo usuário no formulário seguro; nunca aparece para o agente): a Management API (`api.supabase.com`, projeto `zpgzndrgsvynfomjqods` = `clinica-torriceli-testes`, `sa-east-1`) permite ler o estado, aplicar migrações e publicar funções daqui, sempre com aprovação prévia. Aplicar migração: bloco `do` com `execute` da migração + `insert` em `supabase_migrations.schema_migrations` (versão = prefixo do arquivo), para ser tudo-ou-nada e manter o histórico igual ao da CLI; ensaiar antes com o mesmo bloco terminando em `raise exception`. A conexão de leitura (`/database/query/read-only`) não executa funções `security definer`; para conferências use `/database/query` só com `select`. Publicar a função de e-mail: `POST /v1/projects/{ref}/functions/deploy?slug=availability-email` em multipart, com `metadata` `{"entrypoint_path":"supabase/functions/availability-email/index.ts","name":"availability-email","verify_jwt":false}` e um `file` para cada um dos três arquivos (`availability-email/index.ts`, `_shared/availability-email.mjs`, `_shared/resend-webhook.mjs` e, desde a v5, `_shared/booking-email.mjs`, com o caminho a partir de `supabase/functions/` no nome); ensaiar antes com `&bundleOnly=true`, que monta sem publicar. Manter `verify_jwt` falso: o cron chama a função com segredo próprio. Configuração do Auth: `PATCH /v1/projects/{ref}/config/auth` só com os campos a mudar (a resposta do `GET` contém segredos; filtrar antes de exibir). O Postgres direto (TCP) não passa pelo proxy desta nuvem.
